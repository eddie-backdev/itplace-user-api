# Benefit chat API

`POST /api/v1/questions/chat` provides an authenticated, follow-up-aware membership-benefit search. It returns the existing `ApiResponse` envelope with `QUESTION_SUCCESS`; the legacy `GET /api/v1/questions/recommend` contract remains available.

The request body contains `question` (required, up to 500 characters), optional `messages` (up to 12 `user`/`assistant` turns, up to 3,000 characters each), optional `previousCandidateKeys` (up to 8 structured benefit/policy/tier identities), optional paired `lat`/`lng`, and optional `carrier`/`grade`. Membership preferences are also loaded from the authenticated account. Coordinates are never inferred when absent.

The response data contains `reason`, `partners`, `status`, `suggestedQuestions`, and `traceId`. Each partner retains the established benefit summary fields and adds `candidateKey`, `policyId`, `tierBenefitId`, `carrier`, `grade`, `usageType`, `sourceUrl`, and `sourceCapturedAt`. Candidate identities preserve policy and tier distinctions even when a benefit is shared across carriers. Source links are returned only for absolute HTTP(S) URLs.

Structured policy conditions carry `offers`, `offerResolution` (`SINGLE`, `SCOPED`, `PARTIAL`, or `UNRESOLVED`), and `channelDecision`. `SINGLE` keeps canonical grade-specific tier rewards with common conditions; `SCOPED` requires the same offer to match both requested channel and membership grade. `PARTIAL` preserves resolved offers while recording unassigned rules separately; matched grade/channel facts remain usable. `UNRESOLVED` remains discoverable from verified tier facts for broad membership searches with an uncertainty caveat, but is omitted from channel-constrained results. The grounding path preserves scoped offer details and exclusions and does not claim unknown grades as eligible.

Statuses are `ANSWER`, `CLARIFICATION`, `NO_RESULTS`, `UNAVAILABLE`, and `OUT_OF_SCOPE`. Search failures are reported as `UNAVAILABLE`; a completed query with no matching evidence is `NO_RESULTS`. Generic channel requests such as “온라인 혜택” browse active, grade-eligible benefits with known online usage. A nearby request without coordinates returns national benefit evidence and asks the user to allow current-location access or search the region in the map; its GPS-recognized suggestion is “내 주변 매장 찾아줘”. Named regions are not geocoded or silently replaced with device coordinates; the response directs the user to search that region in the map.

`AI_ENABLED` defaults to `false`. In that mode the endpoint skips model and embedding requests and uses bounded lexical database retrieval plus deterministic, evidence-grounded wording. When enabled, `OPENAI_CHAT_MODEL` selects the chat model (the application default is `gpt-5-nano`), and `app.ai.chat.timeout` defaults to eight seconds for chat calls. Embedding failures fall back to query-aware lexical retrieval. The frontend chat request timeout is 45 seconds. No unrelated database-first fallback is used by this endpoint.

The benefit embedding document version is now `benefit-carrier-grade-rag-v3`. Existing indexed documents need the normal benefit RAG reindex/sync before new evidence fields and canonical text are searchable. An earlier local Elasticsearch evaluation used 4,405 policy/tier documents. That is historical evidence, not the state of the PostgreSQL transition or this source repair. The current source work does not index or embed documents, and does not establish production readiness.

Offer-scope changes in this work are preparation-only: they do not call paid embedding services or update an Elasticsearch index. Physical map presence is based on active, business-valid store-linked benefits regardless of redemption channel; a requested carrier remains strict and is never substituted with another carrier. Partner-benefit caches use `partner-benefits-v3` so older processes cannot republish incompatible condition DTOs. Physical-map snapshots retain their separate versioned namespace.

Explicit current topics override stale topic and location context from earlier messages. The answerer receives prior user messages only for a resolved follow-up. Known convenience-store, movie, cafe/dessert, kids-cafe, and study-cafe topics constrain business types before retrieval limits and revalidate returned candidates; multiple recognized topics use a union. Convenience-store metadata recognizes established brands even when the source category is blank or broadly labeled, and lexical fallback includes metadata tags and use cases.

Regression coverage includes request validation and defensive lists, exact previous-key revalidation, distinct policy/tier identities across carrier comparisons, no-results versus unavailable responses, query-aware fallback behavior, grade-unknown tier eligibility, the document builder contract, explicit topic changes after nearby requests, convenience-store classification, and separation of movie/cafe search from unrelated business types.

## Structured source preparation (2026-10-21)

Source blocks retain ordered HTML/JSON paths internally. Offers expose only their matched evidence, typed numeric facts and deduplicated warning codes; unassigned raw fragments and source paths are not part of public or answer-grounding views. Facts distinguish discount/reward values, per-spend bases, minimum spend, spending caps, discount caps, usage periods and shared program limits. Unsupported rules remain source text rather than guessed scalar values.

A source-proven offer does not require an existing canonical tier row to be prepared for RAG. Uncovered offer grades get scoped documents with the existing benefit/policy IDs, the offer key and a null tier ID. Canonical coverage is checked per grade, and retrieval rehydrates the matching offer before answering. No synthetic database tier ID is invented. This is implemented and tested preparation logic; embeddings remain deferred.
