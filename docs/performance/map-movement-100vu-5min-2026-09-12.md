## 입력과 환경

- 160,000개 서로 다른 중심 좌표·URL을 seed `20260911`로 섞어 순환했다. **측정 중 16회 완전 순환 후 45,980건을 더 발행했다. 고유 URL은 160,000개, 반복 발행은 2,445,980건**이다. 매 요청이 새로운 좌표였다고 표현하지 않는다. 예열도 별도 순서로 같은 corpus를 사용한다.
- 매장 anchor 주변 75%, 직사각형 균등 좌표 25%의 합성 분포다. 빈 지역을 포함하며 실제 이용자 지역·줌 분포가 아니다. corpus SHA-256은 `35d9ad7f66d294875a6020178d6bca78c7902fe45de7daa57e5cf4b5ff97f070`이다.
- macOS ARM64, 논리 CPU 12개·메모리 36GiB의 같은 컴퓨터에서 API·DB·Redis·발생기가 자원을 공유했다. 임시 로컬 DB와 전용 Redis를 사용했다.
- API는 SDKMAN Java 17, heap 512MiB~1GiB. 발생기는 SDKMAN Java 11, heap 256MiB~1GiB. DB pool은 replica 20 / source 10이다. HTTP/1.1 keep-alive, `Accept-Encoding: identity`, 사용자 대기 없는 closed-loop다.
- cluster snapshot 준비를 먼저 확인했다. snapshot poll 5초·재검증 30초·최대 경과 60초 설정은 유지했다. **기존 loadtest profile의 정기 materialized view 재계산은 비활성화 상태**다. 그 배경 작업의 비용은 포함하지 않는다.
- 측정 HEAD는 `4f5778f`이며 실행 코드·빌드 설정은 JAR 생성 당시 `df4ff46`과 같았다. 검증된 JAR을 재사용하고 현재 발생기 소스를 Java 11로 다시 컴파일했다. 최근 프론트 요약 계산 제거는 이 직접 API 부하에 영향을 주지 않는다.

## 지속 구간의 관측

10초 간격 Prometheus 표본 34개를 저장했고 수집 오류는 없었다. 측정 내부로 추정한 28개 구간, 약 280.294초에서 서버 처리량은 **7,186~9,166 TPS**, Spring HTTP timer 평균은 4.954~6.615ms였다. 첫 여섯 구간의 가중 처리량은 약 8,137 TPS, 마지막 여섯 구간은 약 8,733 TPS였다. 끝까지 처리량이 붕괴하는 현상은 관측하지 않았다.

이 구간 평균은 Spring의 서버 관측 경계 값이며 위 표의 클라이언트 응답 시간과 다르다. 발생기가 phase별 정확한 wall-clock 시작 시각을 기록하지 않아 내부 구간 경계는 추정치다. **전체 300초 TPS·평균·백분위는 발생기의 measurement만 사용한다.**

- Replica 연결 획득 대기는 예열·측정·drain 전체 연결 작업당 평균 2.856ms, 보유는 2.853ms, timeout 0이었다. 10초 표본에서 관측한 pending 최대는 76개이며 연속 측정 최대값은 아니다.
- 내부 구간의 API CPU는 약 4.19~5.90코어, 공유 호스트 CPU gauge는 약 98.3~99.8%였다. 발생기·DB도 같은 자원을 사용하므로 이를 API 서버 단독의 최대 처리량으로 확정하지 않는다.
- API heap 표본은 약 157.1~417.7MiB, 해당 구간 GC pause 누적은 5.946초였다. 5분 표본은 장기 메모리 누수 부재를 증명하지 않는다.

## 검증·정리·해석 범위

예열 포함 클라이언트 요청은 2,742,686건이며 서버의 두 지도 URI counter 합계와 일치했다. 키워드·주변 검색·모바일 요청은 0건이다. 전체/그룹 건수·가중 평균·TPS 분모·순환 횟수와 JAR/입력 해시를 별도로 검산했다.

직전에 완료된 15초 사전 시험은 5,018.43 TPS, 평균 19.860ms, 오류 0이었다. 사용자 요청으로 최종 5분 시험을 별도 환경에서 실행했으며 두 결과의 차이는 코드 개선률이 아니다. [이전 1·5·10개 단기 시험](map-movement-only-2026-09-11.md)과도 예열·시간·누적 상태가 다르므로 최대 TPS나 동시성에 따른 성능 곡선으로 연결하지 않는다.

작업이 만든 API·발생기·임시 DB·Redis를 정리하고 기존 서비스 보존을 확인했다. [정리 증거](evidence/2026-09-12/map-movement-100vu-5min/cleanup.json). 제품 코드 변경·운영 DB 변경·배포·push는 수행하지 않았다. 애플리케이션 코드가 같아 Gradle 전체 검사/build를 새로 실행한 것으로 보고하지 않는다.

원본 corpus·JAR·Prom·실행/분석 스크립트는 `output/map-movement-100vu-5min-2026-09-12/`에, 15초 사전 시험은 `output/map-movement-100vu-2026-09-12/`에 보존한다. 이 결과는 **해당 로컬 조건에서 100개 작업자로 5분 동안 처리한 성능**이며 클라우드 운영 성능·실제 사용자 100명의 행동·서버 최대 용량을 입증하는 값은 아니다.
