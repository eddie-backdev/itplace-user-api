# 지도 TPS·평균 응답시간의 잔여 병목과 외부 서비스 비교

> **범위 정정:** 이 보고서의 웹 혼합 시험에는 키워드·주변 검색이 포함됐다. 사용자가 요청한 **지도 이동만의 병목**을 판단하는 기준으로 사용할 수 없다. 키워드 개선을 먼저 진행하자는 아래 우선순위는 이번 지도 이동 작업에서 철회한다. 기존 수치와 검색 코드 조사는 당시 범위의 기록으로 보존하며, 현재 대상은 화면 내 매장 preview와 cluster 두 API다. [지도 이동 전용 재확인](map-movement-only-2026-09-11.md)을 따른다.

조사일: 2026-09-11. 대상은 user-api `df4ff46`의 실행 코드와 user-front `eb48e13`이다. 후속 문서 commit은 실행 코드를 바꾸지 않는다. 모바일은 부하 대상에서 제외한다. 이 문서는 진단과 제안이며 아래 새 구조를 구현했다는 기록이 아니다.

## 판단

직접 확인한 큰 지연은 **DB 연결 대기와 Spring 관측 경계 밖의 공통 대기**다. 이미 예열된 클러스터도 이 부하의 영향을 받는다. 코드에서 확인한 반복 작업은 새 위치마다 매장 후보와 혜택 적용 조건을 구하고, 검색에서는 ES와 DB가 후보 찾기를 나눠 수행하는 구조다. 이 중 어떤 변경이 전체 처리량을 가장 크게 높이는지는 소규모 분리 검증으로 확인해야 한다.

혜택 Redis hit는 혜택 원본 조회를 생략한다. 위치 SQL, 결과 객체 생성, Redis JSON 해석, 응답 조립까지 생략하는 것은 아니다. 현재 정상 클러스터는 공용 집계 snapshot을 재사용하므로 이 설명에서 제외한다. 이 구분이 다음 개선의 핵심이다.

## 현재 수치의 의미

### 사용자 지시에 따른 소규모 확인

같은 corrected JAR로 **동시 요청 1·5·10개, 각 5초**만 확인했다. 웹 혼합은 기존 전국 corpus의 preview 50%·cluster 30%·keyword 10%·nearby 10% 구성이다. 각 단축 실행의 실제 소비 prefix와 비중은 조금씩 다르다.

| 단회 진단 | 완료 / 오류 | TPS | 평균 | p95 |
|---|---:|---:|---:|---:|
| 웹 혼합 1개 동시 요청 | 551 / 0 | 110.16 | 9.05ms | 45.28ms |
| 웹 혼합 5개 동시 요청 | 2,497 / 0 | 496.53 | 10.00ms | 55.25ms |
| 웹 혼합 10개 동시 요청 | 3,388 / 0 | 671.77 | 14.66ms | 73.00ms |
| 클러스터만 1개 동시 요청 | 25,565 / 0 | 5,112.82 | 0.19ms | 0.24ms |

API Java 17·발생기 SDKMAN Java 11, 같은 로컬 host·512MiB~1GiB API heap·HTTP identity 조건이다. 동일 API를 순서대로 사용했고 1/5 웹과 cluster의 예열은 1초, 웹 10은 별도 예열 없이 앞선 실행의 상태를 이어받았다. 웹 완료 **6,436건**, cluster **25,565건**, 오류 0. 각 측정 안의 요청 URI 재사용·corpus 순환은 0이며 회차 사이 재사용은 가능하다.

이것은 **작은 부하에서 이미 짧게 처리되고, cluster 자체는 매우 가볍다**는 진단 근거다. 5초 단회·짧은 예열 결과이므로 운영 용량·장기 안정성·변경 전후 개선률로 쓰지 않는다. 클러스터 전용의 5,113 TPS를 전체 지도 검색 TPS로 주장하지 않는다. [소규모 원본 요약](evidence/2026-09-11/map-root-causes/small-summary.json).

계획 변경 이력: 후속 지시 전에 시작한 50개 prewarm·웹 1/50 단축 실행은 별도 중간 기록으로 남겼다. 지시 전환 중 시작된 200개 실행은 중단되어 결과에서 제외했고, 예정한 **500개 실행·500개 thread dump는 수행하지 않았다**. 앞으로 500명 시험은 개선 구현과 소규모 검증 이후에 수행한다.

### 기존 정식 비교 기록의 해석

[최근 정식 비교](web-preview-regression-2026-09-11.md)의 최종 구현은 로컬 웹 혼합 500개 동시 요청에서 **1,140.37 TPS, 평균 435.71ms, 회차별 p95 803.08~819.22ms**였다. 개선 전보다 빨라졌지만 저지연 목표를 달성했다고 판단할 SLO·운영 부하 근거는 없다.

| 같은 혼합 부하 안의 경로 | 평균 응답시간 |
|---|---:|
| 화면 안 개별 매장 preview | 448.24ms |
| 키워드 검색 | 710.98ms |
| 주변 조회 | 619.81ms |
| 클러스터 level 5 / 7 / 10 | 261.44 / 261.67 / 262.02ms |

이 값은 HTTP body를 모두 받은 시점까지이며 개별 SQL 실행시간이 아니다. API·PostgreSQL·Redis·ES·발생기가 같은 Apple M3 Pro의 자원을 공유한다. 운영 서버의 현재 성능이나 각 경로 단독 성능으로 사용하지 않는다.

발생기는 응답이 끝나면 다음 요청을 보내는 closed-loop다. `1,140.37 × 0.43571 ≈ 497`로, 500개 동시 요청과 거의 맞는다. 이 조건에서는 처리량과 평균 지연이 서로 연결되며, 500명의 사람이 생각하는 시간 없이 계속 검색하는 과부하 시험에 가깝다. 실제 사용량에 맞는 처리 가능 RPS는 도착률을 독립적으로 올리는 시험도 필요하다. [Grafana k6의 open/closed model 설명](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

## 요청마다 남은 일

### 1. 키워드 검색의 전역 후보 탐색과 두 검색 엔진 왕복

정상 ES 응답 경로도 다음 단계를 순서대로 실행한다.

```text
ES msearch: 브랜드 후보 100 + 이름/업종 후보 200
    → DB: 가까운 문자열 일치 매장 최대 30개 보충
    → 후보 ID 병합
    → DB: Store + Partner 엔티티 조회와 적격 조건 재검사
    → 브랜드 분류·그룹별 거리 정렬
    → Redis: 제휴사 혜택 MGET / JSON 해석
    → 응답용 거리 계산·공통 혜택 조립·JSON 응답
```

현재 ES 검색에는 사용자 좌표가 전달되지 않는다. `StoreDocument`와 인덱스 생성 매핑에도 좌표가 없으며, 시작 시 seed는 기본 비활성이고 기존 ID를 건너뛴다. 즉 현재 앱 코드의 ES 문서는 최신 위치와 적격 상태를 갖춘 완결된 지도 읽기 데이터가 아니다. 운영 ES에 별도 writer/추가 매핑이 있는지는 이번 조사로 확정하지 않았다.

전국 ES 후보 상한 밖의 가까운 매장을 놓치지 않으려고 **현재 구현은 ES 성공 여부와 무관하게 DB 보충을 실행한다**. DB 보충도 공간으로 범위를 먼저 제한하는 쿼리가 아니라 전국 문자열 후보를 만든 뒤 거리순으로 고르는 쿼리다. 이 보충만 제거하면 가까운 결과 누락 문제가 다시 생길 수 있다. keyword의 후보는 중복 제거 전 최대 330개이며 최종 500개 제한은 없다.

수정된 `편의점` custom plan은 기존 GIN 인덱스를 사용하면서도 **후보 36,898개 → 적격 29,709개 → 최종 30개**를 처리한다. 별도 SQL 진단의 중앙값은 **79.064ms**다. `다` 같은 짧고 흔한 검색어는 후보를 충분히 줄이지 못한다. “인덱스가 없다”가 원인이 아니라 **현재 검색 범위와 순위 계약에 비해 요청당 검사량이 많다**는 문제다. [실행 계획과 비교 조건](web-preview-sql-regression-2026-09-11.md).

앞선 UNION 임시 디스크 쓰기와 불리한 generic plan은 수정된 문제다. 이를 현재 그대로 남은 병목으로 다시 집계하지 않는다.

### 2. 상세 지도·주변 조회의 위치 결과는 아직 매번 계산

개별 매장 preview는 공간 인덱스로 화면 후보를 찾지만 활성 매장·제휴사·혜택·정책 조건을 읽을 때 결합한다. 저장된 정규화 컬럼은 문자열 정규화 비용을 옮긴 것이며, “지도에 표시 가능한 매장”을 완성된 읽기 데이터로 저장한 것은 아니다.

주변 compact도 반경 안 적격 ID 조회와 최종 Store/Partner 조회를 나눠 실행한다. 최대 900개 후보 중 기존 무작위 표본 최대 300개를 고른다. 키워드와 주변 경로에는 full entity 조회가 남아 있다. SQL 결과를 곧바로 표시용 최소 데이터로 받을 수 있는지 검토할 가치가 있지만, 그 이득의 크기는 아직 분리 측정하지 않았다.

새 좌표가 와도 재사용하는 것은 제휴사 혜택이며, 인접 화면들의 공통 매장 후보를 서버가 고정 공간 단위로 재사용하는 경로는 아직 없다. 프론트의 30초 coverage 재사용은 작은 이동을 줄여주지만, 서로 다른 사용자나 화면 밖 이동까지 공유하지 않는다.

### 3. 연결 대기와 공유 자원 경합

최근 정식 비교의 replica 연결 획득 평균은 **184.60ms**, 연결 보유 평균은 **20.86ms**였다. 이는 예열·측정·drain·배경 작업을 포함한 counter이며, HTTP 측정 창과 다르다. 한 요청이 연결을 여러 번 얻을 수 있으므로 `184.60 / 435.71`로 DB 대기 비율을 계산하지 않는다.

연결을 기다리는 동안 동기 요청 스레드가 점유되고, 빠른 클러스터도 혼합 부하에서 영향을 받는다. 다만 기존 HTTP 평균만으로 Servlet 큐·OS 스케줄링·발생기 지연을 각각 몇 ms라고 확정할 수는 없다. 추가 원시 지표와 격리 진단은 별도 근거로 보존한다.

기존 3회 원시 telemetry를 다시 분석한 결과는 다음과 같다. 각 회차의 측정 내부에서 보수적으로 선택한 약 40.7~41.2초·19개 표본이다. 원래 45초 전체와 같지 않으며 gauge는 시간 가중, counter는 첫/마지막 표본 차이로 계산했다.

| 관측 항목 | 3회 범위 | 해석 |
|---|---:|---|
| Replica 사용 중 연결 | 평균 19.45~19.94 / 최대 20 | 거의 계속 사용 중 |
| Replica 연결 대기 | 평균 173.35~176.04개 | 요청 스레드가 DB 앞에서 대기 |
| 연결 획득 / 보유 | 평균 174.15~175.79 / 19.45~19.60ms | SQL 자체보다 긴 연결 획득 대기. 보유 시간은 순수 SQL 시간이 아님 |
| API CPU | 평균 1.77~1.90코어 | API 프로세스가 12코어를 모두 소진한 증거는 아님 |
| 전체 host CPU 지표 | 평균 99.54~99.57% | 같은 host의 DB·발생기 등 소유자별 분리는 기존 지표만으로 불가 |
| Heap 표본 / 최대 heap | 192.7~424.6MiB / 1GiB | 이 구간에 heap 용량 부족이 주원인이라는 근거 없음 |
| GC pause 누적 | 0.534~0.556초, 약 1.3% wall | GC pause만으로 수백 ms 평균 지연을 설명하지 못함. 장기 누수 검사는 아님 |
| Cluster snapshot | 회차별 hit 13,995~14,125, fallback 0 | 정상 공유 snapshot 경로가 사용됨 |

별도로 **예열+측정의 요청 수가 클라이언트와 Spring counter에서 경로별로 일치하는 전체 구간**을 비교했다. 위 측정 내부나 정식 측정 평균과 섞지 않는다.

| 경로 | 클라이언트 평균 | Spring 관측 평균 | 두 평균의 차이 |
|---|---:|---:|---:|
| Cluster 합계 | 282.38~285.80ms | 0.72~3.63ms | 278.96~283.34ms |
| Preview | 482.56~489.53ms | 203.12~206.07ms | 279.44~283.46ms |
| Keyword | 739.69~750.70ms | 461.97~468.59ms | 277.73~282.97ms |
| Nearby | 661.81~667.96ms | 382.17~384.16ms | 279.64~283.81ms |

모든 경로에 거의 같은 약 280ms가 Spring 관측 경계 밖에서 더해진다. 이는 **클러스터 조회 계산이 280ms 걸린다는 해석을 반박하는 직접 근거**다. 그러나 합계 counter 차이는 요청별 tracing이 아니며, 차이 전체를 Tomcat queue 시간으로 동일시할 수는 없다. 서버 진입 전 대기, 관측 filter 밖 처리, 전송, 발생기 스케줄링을 포함한다.

풀 크기를 늘리면 대기가 다른 곳으로 이동할 수 있다. DB가 이미 처리 자원을 소진했다면 더 많은 동시 쿼리는 처리량을 오히려 낮출 수 있으므로, 연결 수는 DB 처리 비용을 줄인 후 다시 조정한다. [HikariCP 공식 pool sizing 설명](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing).

### 4. compact 이후에도 JSON과 혜택 조립은 남음

현재 혼합 부하의 평균 body는 preview 약 27KB, 주변 약 61KB, 검색 약 14KB다. 공통 혜택 중복 전송은 줄였지만 요청마다 Redis의 혜택 JSON을 해석하고 미리보기를 조립한다. 이 비용은 없어지지 않았으나 현재 corrected 실행의 CPU profile 없이 주 병목 비율을 단정하지 않는다.

이 부하 시험은 `Accept-Encoding: identity`다. 이미 구현된 gzip이 운영 네트워크 전송량을 줄일 수 있지만, SQL 검사량이나 연결 대기를 제거하지는 않는다.

## 다른 서비스가 공개한 방식

아래는 공식 공개 문서에서 확인되는 구조와 API 계약이다. Google·Kakao 내부의 DB·Redis 구성이나 사내 TPS를 확인한 자료는 아니다. 우리 서비스가 이미 사용하는 Kakao 배경 지도와 우리가 별도로 제공하는 혜택 매장 마커도 구분한다.

| 서비스·자료 | 확인된 방식 | ITPLACE에 적용할 원리 |
|---|---|---|
| [Mapbox Vector Tiles API](https://docs.mapbox.com/api/maps/vector-tiles/) | 고정 `tileset/z/x/y`로 타일 요청. 공식 기본 cache header는 단말 12시간·CDN 5분. 스타일에 보이지 않는 feature를 제외하는 최적화도 지원 | 임의 viewport 응답 대신 재사용 가능한 고정 공간의 공개 마커 데이터를 캐시. 우리 혜택의 최신성 요구에 맞는 TTL·버전 사용 |
| [Google Places FieldMask](https://developers.google.com/maps/documentation/places/web-service/choose-fields), [Place Details](https://developers.google.com/maps/documentation/places/web-service/place-details) | 검색과 단일 장소 상세에서 필요한 필드를 명시. 불필요한 필드 제거가 처리 시간·응답량을 줄인다고 설명 | 마커 표시, 카드 목록, 선택 매장의 상세를 필요한 시점과 필드에 따라 나누기 |

| [Kakao Local API](https://developers.kakao.com/docs/ko/local/dev-guide) | keyword 검색의 좌표/반경/rect/거리순 정렬 지원. category 검색은 반경 또는 rect가 필수. 한 페이지 최대 15개와 후속 페이지 제공 | 전국 후보를 잘라 받아 애플리케이션에서 가까운 항목을 찾는 대신 검색 엔진에 공간 조건 전달 |
| [Uber H3 기술 글](https://www.uber.com/qa/en/blog/h3/) | 위치 이벤트를 계층적 공간 셀로 묶어 분석·수급 최적화·시각화에 활용 | 미세하게 바뀌는 좌표를 안정적인 공간 단위로 묶기. 이 글을 Uber 장소 검색 API의 캐시 구현 증거로 사용하지 않음 |

Mapbox는 큰 GeoJSON을 서버에서 타일로 만드는 방법도 안내한다. 이는 전체 전국 데이터를 브라우저에 먼저 넣어야 한다는 뜻이 아니다. 필요한 공간 조각을 가져오는 선택지가 있다. [Mapbox의 큰 GeoJSON 처리 안내](https://docs.mapbox.com/help/troubleshooting/working-with-large-geojson-data/).

타사의 검색 결과 상한 15/20은 우리 상세 지도 상한 300을 정당화하는 근거가 아니다. 검색 목록과 화면 안 전체 마커는 다른 계약이다. 현재 LIMIT을 제거하는 것만으로 전역 후보 검사나 혜택 조건 결합 비용이 없어지지도 않는다.

## 권장 순서와 설계 경계

아래 후보들은 당시 웹 혼합 조사에서 나온 안이다. **키워드의 전역 후보 탐색·중복 DB 조회를 현재 지도 이동 개선의 첫 순위로 둔 판단은 철회한다.** 이번 범위에서는 화면 내 preview의 위치 SQL·혜택 처리와 cluster snapshot 경로만 확인한다. 키워드·주변 검색 개선은 별도 작업으로 분리한다.

### 지도 이동: 표시용 읽기 데이터를 고정 셀로 재사용

지도 이동에서 우선 검증할 구조적 개선 후보는 **지도에서 쓸 공개 매장 정보와 표시 가능 여부를 갱신 시점에 준비하고, 고정 공간별로 재사용하는 것**이다. 현재 클러스터가 이미 쓰는 사전 계산 원리를 개별 매장 표시에도 적용한다. 현재 작은 혜택·정책 집합의 쿼리 내 1회 aggregate는 약 0.35ms였으므로 그 부분 하나를 제거하는 것만으로 큰 개선이 난다고 주장하지 않는다.

```text
수집·혜택 변경
  → 표시 가능한 매장 읽기 데이터 갱신
  → 고정 셀별 ID·좌표·partnerId·필요한 표시 필드
  → Redis 공유 캐시

화면 이동
  → 화면과 겹치는 셀 선택
  → 캐시에서 매장 후보 결합
  → 실제 bounds 필터·ID 중복 제거
  → 필요한 공통 혜택과 응답
```

예를 들어 이전 화면이 A·B·C·D 셀, 새 화면이 B·D·E·F 셀과 겹치면 B·D는 그대로 재사용한다. 같은 셀 안에서 조금 움직이면 후보 데이터가 재사용된다. 캐시 key에 정확한 화면 모서리 좌표를 넣을 필요가 없다.

가장 작은 실험은 현재 응답 계약을 유지하면서 **공개 후보 데이터만 Redis 셀 단위로 공유**하는 방식이다. 처음부터 MVT·CDN·H3 라이브러리·전국 데이터를 가진 새 JVM L1을 모두 도입할 필요는 없다. 익숙한 고정 사각 격자로 시작해도 원리를 검증할 수 있다.

후보 셀에 viewport 기준 top-300 결과를 저장하면 다른 화면에서 누락이 생긴다. 셀은 해당 범위의 완전한 후보를 보관하거나 더 작게 분할해야 한다. 거리·사용자별 결과를 공유 후보에 섞지 않는다. 메모리/응답 크기 상한, 빈 셀 캐시, 갱신 후 관련 셀·제휴사 무효화와 버전 일관성을 함께 설계해야 한다. 한 번도 방문하지 않은 셀은 lazy cache에서 여전히 DB를 읽으므로 cold/warm을 따로 측정한다.

공개 데이터가 더 안정되고 응답 계약을 나눌 때 버전이 있는 HTTP 타일과 CDN으로 확장할 수 있다. 여러 API 서버는 Redis/읽기 데이터의 같은 버전을 공유하고, 각 서버에 전국 원본을 중복 보관할 필요는 없다. 이 효과는 아직 측정하지 않았으므로 예상 TPS 배수를 제시하지 않는다.

### 키워드: 후보 탐색에 좌표·적격 조건을 함께 적용

기존 ES 문서에 `geo_point`와 검색에 필요한 적격·표시 필드를 갖추고, 브랜드 우선순위와 거리순 후보를 검색 단계에서 받는 안을 비교한다. ES는 공간 범위 필터·거리 정렬을 공식 지원한다. [Elasticsearch geo_point](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/geo-point).

핵심은 ES 사용 자체를 늘리는 것이 아니라 정상 경로의 “ES 전국 후보 + 매번 DB 보충 + full entity 재조회”를 줄이는 것이다. 기존 전국 검색을 임의의 작은 반경으로 바꾸면 결과 계약이 달라진다. 브랜드 정확 일치 우선, 형태소/문자열 차이, 가까운 결과 누락, 동률 순서, 색인 지연·삭제·장애 fallback을 먼저 대조해야 한다.

데이터 크기상 PostGIS만으로 계약을 만족시키는 안도 비교 대상이다. KNN 거리 인덱스는 가능하지만 기존 `ST_DistanceSphere`와 우선순위를 그대로 보존하는지는 별도 검증해야 한다. [PostGIS nearest-neighbour 설명](https://postgis.net/workshops/postgis-intro/knn.html). 두 엔진을 유지해야 한다고 미리 결론내리지 않는다.

### 응답 조립: 표시 데이터와 카드·상세 혜택 조립 분리

초기 마커에 ID·좌표·표시 분류를 제공하고, 실제 보이는 카드 또는 선택 매장에 필요한 혜택을 batch로 가져오는 안이다. 이미 compact가 공통 혜택을 묶었으므로 중복 제거만 반복하지 않는다. 현재 카드에서 즉시 필요한 정보가 있다면 먼저 표시할 수 있도록 유지하고, 매장별 1요청씩 보내는 N+1 네트워크 구조를 만들지 않는다.

### 후속 검증

- 사용자의 후속 지시에 따라 원인 확인은 **동시 요청 1·5·10개 정도의 짧은 시험**으로 진행한다. 500명 시험은 개선 구현과 소규모 확인 뒤의 최종 검증으로 미룬다. 이 문서의 기존 500회차 재분석은 과거 원본을 읽은 것이며 새 500명 실행이 아니다.
- 동일 응답 계약의 변경은 같은 전국 입력·API 비중으로 전후 비교한다. 별도 “지도 이동만” 시나리오를 혼합 성능 개선률로 바꾸어 쓰지 않는다.
- 셀 캐시는 동일 좌표뿐 아니라 인접 이동·다른 사용자 공유·새 지역 cold miss를 구분하고 DB 요청 수와 후보 재사용률을 측정한다.
- 검색 구조 변경은 ID/순위 동등성과 DB 왕복 감소를 먼저 확인한다.
- CPU 비용, 연결 점유/대기, 할당량, p95를 함께 보고 최종적으로 클라우드와 분리된 발생기에서 도착률별 한계를 확인한다.
- 이번 연구가 운영 배포 상태를 확인한 것은 아니다. 최근 로컬 변경의 실제 서버 적용 여부와 운영 자원 지표는 별도 확인 대상이다.
