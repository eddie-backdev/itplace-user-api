# 웹 지도 후속 개선 · 포트폴리오 사례

> 아래 두 변경의 최초 통합 단계는 속도 목표를 통과하지 못했다. 이 중간 결과를 성공 사례로 제시하지 않고 마지막 절의 회귀 원인·수정·재검증까지 함께 설명한다.

기준 구현은 앞선 개선판 `b9401d8`, 중간 구현은 user-api `7cc730f`와 user-front `2dfda51`, 최종 후속 수정은 user-api `df4ff46`과 user-front `eb48e13`이다. 최초 개발 시점부터의 누적 개선률로 설명하지 않는다. 모바일은 부하 대상에서 제외했다. [중간 실험](web-preview-renewal-2026-09-11.md)과 [최종 재검증](web-preview-regression-2026-09-11.md)의 수치를 섞지 않는다.

**성과의 범위:** 동일 질의의 JSON body 50.0% 감소와 검색 결과 누락 감소를 확인했다. 로컬 500개 동시 요청, 전후 3회 비교는 975.22→949.09 TPS, 평균 508.08→522.42ms로 소폭 저하됐다. 총 측정 263,715건에서 오류는 없었지만 TPS 향상을 입증한 사례로 설명하지 않는다.

## 사례 7. 읽을 때마다 하던 정규화를 쓰기로 이동하고 LIMIT 순서 수정

**문제:** 매장이 제휴사와 연결돼 있어도 조회할 때마다 원본 이름을 정규화하고 별칭·업종을 검사했다. SQL에서 이미 후보를 제한한 뒤 Java에서 걸렀기 때문에, 부적격 후보가 앞에 몰리면 뒤에 있는 정상 매장을 채워 주지 못했다.

**판단:** 매장·제휴사 연결의 원천 정확성까지 보장하는 새 데이터 파이프라인을 이번 범위에 추가하지 않았다. 기존 판정 규칙을 유지하면서 반복되는 문자열 정규화와 후보 제한 순서를 바꿨다.

**구현:** 매장 이름·업종과 제휴사 이름은 PostgreSQL stored generated column으로 변경 시 계산한다. 조회에서는 현재 두 행을 조인하고 정규화된 문자열로 포함 관계·GS25/CU/세븐일레븐 별칭·다락 업종을 확인한 뒤 LIMIT을 적용한다. 웹 최종 ID 조회도 현재 DB 값으로 검사하므로 오래된 ES ID를 그대로 신뢰하지 않는다. 기존 모바일/상세 경로는 유지한다.

**검증:** 실제 PostGIS에서 부적격 후보 305개 뒤의 정상 매장 300개 반환, 반경·키워드 LIMIT 전 검사, 이름·업종·제휴사 변경 후 반영, 기존 모바일 후보 집합 보존을 확인했다. Java 17이 정의한 Unicode 전체 입력을 이용해 SQL 정규화와 기존 Java 규칙의 일치를 검사했다. [30개 scoped 검증](map-read-eligibility-2026-09-11.md), [최종 전체 420개 검증](evidence/2026-09-11/web-preview-tests.json).

**한계:** 관계 판정 자체는 여전히 조회 SQL에서 수행한다. 원천 매장 연결 오류를 모두 수정한 작업도 아니고, 모든 검색 정규화를 없앤 것도 아니다. 생성 컬럼 추가에는 테이블 rewrite·잠금·WAL 비용이 있어 운영 적용을 별도로 확인해야 한다.

**면접 설명:** “읽기가 빈번하고 매장 이름 변경은 드물다는 점을 활용했습니다. 문자열 정규화는 쓰기 시 계산하고, 현재 제휴사와의 관계 판정은 읽기에서 유지했습니다. 단순히 필터를 지우지 않고 LIMIT 앞에 배치해 정상 매장이 후보 제한 때문에 누락되는 문제도 함께 줄였습니다.”

## 사례 8. 캐시에 적중한 뒤의 공통 혜택 조립·전송 중복 제거

**문제:** Redis에서 제휴사 혜택을 한 번 가져와도, 검색·주변 응답을 만들 때 같은 브랜드의 등급 혜택을 매장마다 다시 선택·조립하고 JSON에 반복했다. DB나 Redis 명령 수만으로는 이 비용을 설명할 수 없었다.

**구현:** 주변·카테고리·검색에 `data: {stores, partners}` compact 응답을 추가했다. 제휴사 공통 혜택은 요청 안에서 한 번 준비하고 `partners`에 한 번 전송한다. 매장은 partnerId로 참조한다. 매장명별 예외 혜택은 store.tierBenefit override로 유지하며, 빈 배열도 명시적인 값이다. 브라우저는 기존 카드 데이터로 복원하되 검색의 브랜드 우선 순서·서버 거리 0·주소 필드를 보존한다.

```mermaid
flowchart LR
    DB[유효한 매장 후보] --> CACHE[제휴사 혜택 MGET]
    CACHE --> PREP[요청 안에서 제휴사별 혜택 준비]
    PREP --> RESPONSE[stores 참조 + partners 공통 혜택]
    RESPONSE --> WEB[기존 카드 데이터로 복원]
```

**호환성:** 기존 endpoint는 유지한다. 프론트는 새 endpoint가 없는 404/405에만 legacy 요청을 보낸다. 기존 viewport compact의 partner 혜택은 첫 매장 기준이라는 이전 의미를 보존하고, 다른 매장에 필요한 차이만 optional override로 추가한다. 구버전 프론트가 이미 읽던 필드를 다른 의미로 바꾸지 않았다.

**검증:** 서비스 회귀 테스트에서 300개 매장이 같은 혜택을 사용할 때 tier 목록을 한 번 읽어 조립하는 것을 확인했다. 압축 이전 JSON 크기 검사와 별개로, 공통·오프라인 우선·매장별 예외·빈 예외를 포함한 모든 기존 응답 필드의 복원을 검사했다. 서버 전체 420개 검사와 프론트 계약 테스트·lint·build가 통과했다. 실제 React 카드에서도 검증용 응답으로 순서·혜택·거리 표시를 확인했다. 이 화면 검증은 Kakao SDK/지도 타일 또는 운영 API의 성능 검증이 아니다.

실제 HTTP 104개 동일 질의의 JSON body는 4,576,960→2,287,934 B로 50.0% 감소했다. 공통 매장 2,089개의 필드가 모두 일치했고, 검색 18개 질의는 기존 결과를 유지하며 유효한 매장을 추가해 30개를 채웠다. 응답량 감소와 누락 방지는 확인했지만 이 수치를 TPS 개선률로 바꾸어 설명하지 않는다.

**한계:** Redis JSON 역직렬화는 요청마다 남는다. 새로운 영구 혜택 L1을 추가한 것이 아니므로 서버 수·장기 보관량을 늘려 성능을 얻은 변경으로 설명하지 않는다. 응답 바이트 감소율, SQL 시간, HTTP TPS는 서로 다른 측정 단위다. 각 효과를 전체 개선률에 중복 귀속하지 않는다.

**면접 설명:** “캐시 적중 이후에도 같은 브랜드 혜택을 매장 수만큼 조립하고 전송하고 있었습니다. 응답에서 공통 데이터를 분리하고 매장별 차이만 남겼습니다. 단순히 필드를 삭제해서 빠르게 만드는 대신, 브라우저에서 기존 데이터가 정확히 복원되는지와 검색 순서를 검증했습니다.”

## 후속 수정. 응답량 감소 뒤에 가려진 SQL 회귀 제거

**문제 재정의:** 위 단계는 응답량을 줄였지만 웹 혼합 부하에서 더 느려졌다. 속도 목표를 통과한 것으로 판단할 수 없어, 기능 변경을 유지한 채 실제 SQL 작업과 실행계획을 분리해 비교했다.

**직접 원인:** 키워드 후보 CTE의 UNION 중복 제거 대상에 정규화 문자열 두 열이 추가됐다. `편의점`의 36,898개 중간 후보에서 임시 디스크 쓰기가 678→1,814 blocks로 늘었다. 상세 viewport LIMIT 정렬은 확인한 넓은 영역에서 약 1.9ms였으며 주 회귀를 설명하지 못했다.

**선택:** 두 검색 분기가 겹치지 않게 만들어 `UNION ALL`로 합치고, `NOT MATERIALIZED`로 중간 저장을 제거했다. ID만 합친 뒤 재조인하는 대안은 다른 검색어에서 더 느려져 기각했다. 실제 입력 24개를 순서대로 바인딩하면 custom 5회 뒤 generic 19회를 선택해 짧은 검색어에 불리한 계획이 반복됐다. 그래서 웹 keyword의 짧은 read-only DB transaction에만 `force_custom_plan`을 적용했다. 데이터 캐시를 추가하거나 DB 전역 설정을 변경하지 않았다.

**검증:** 조회 개수·반경·입력 비율은 유지했다. 동일한 171개 HTTP 질의의 매장 집합과 5,273개 매장의 모든 필드가 일치했고, 두 질의의 동일 좌표·우선순위 매장 순서만 storeId 기준으로 안정화됐다. Backend 전체 423개 테스트와 commit/rollback 이후 연결 설정 복구 검증이 통과했다. [SQL 진단·기각안](web-preview-sql-regression-2026-09-11.md)과 [새 기준 버전 대조 부하 결과](web-preview-regression-2026-09-11.md)를 근거로 사용한다.

최종 로컬 웹 혼합 비교는 500개 동시 요청·전후 3회에서 기준 `b9401d8` 대비 **1,014.43→1,140.37 TPS(+12.42%), 평균 488.88→435.71ms(-10.88%)**였다. 세 쌍 모두 개선됐고 총 294,697건 오류 0, 각 측정의 URI 재사용은 0이었다. 기존 실패 실험의 949 TPS와 새 수정판을 직접 연결한 배수가 아니며, 응답 용량·SQL 단독 수치를 HTTP 개선률에 중복 귀속하지 않는다.

**면접 설명:** “응답량을 절반으로 줄였는데 처리량이 떨어졌습니다. 이를 성공으로 포장하지 않고 같은 조건에서 SQL을 분리해 확인했습니다. 문자열 열이 늘어난 중간 집합의 디스크 쓰기와 검색어에 맞지 않는 공통 실행계획을 확인했고, 결과를 줄이지 않고 그 비용을 제거한 뒤 API 부하로 다시 검증했습니다.”
