# 혜택 챗봇·PostgreSQL 통합 준비 메모

목적은 현재 구현과 증거를 바탕으로 다음 구현 작업의 범위·계약·검증 조건을 정하는 것이다. 이 문서는 준비안이며 런타임 변경, 모델 호출, 성능 수치 주장을 포함하지 않는다. 코드 경로는 `itplace-user-api/` 기준이다.

> **후속 개발 반영 — 2026-10-21:** 아래 10월 20일 baseline의 `698개 활성 정책 모두 BOTH`는 과거 상태다. 기존 `develop_server`의 `itplace` DB(5432)에서 정책 1,052건을 재판정해 1,015건의 `usagetype`만 교정했다. 전체는 ONLINE 198 / OFFLINE 241 / BOTH 37 / UNKNOWN 576이며, 활성 698건은 각각 189 / 239 / 37 / 233건이다. 10월 19일 보관 공식 원문과 식별자를 대조한 665건, 기존 이용 안내를 사용한 387건을 대상으로 했으며 라이브 최신성 검증을 뜻하지 않는다. 활성 미확인 233건은 안내문 없음 15건, 명시적 이용 경로 근거 부족 218건으로 남겼다.
>
> 수집기는 할인·혜택을 실제 적용받는 경로를 판정한다. 쿠폰 발급, 앱 바코드 표시, 매장 조회, 이용 불가 문구만으로 온라인/오프라인을 추정하지 않는다. 프론트의 브랜드별 덮어쓰기는 제거했고 UNKNOWN은 확인 필요로 표시한다. 관리자 테스트 176건(0 skip), 프론트 테스트 78건, 빌드 및 실제 API의 6개 통신사·이용 방식 필터와 상세 화면을 검증했다. 백업 복원 리허설과 비채널 데이터 불변 검증을 완료했다. 근거·미확인 목록·백업은 `/Users/eddie/.local/state/itplace/usage-channel-repair-20261021`에 보존한다. 운영 배포, ES 갱신, 유료 AI/임베딩 실행은 하지 않았으며 이 교정만으로 임베딩 준비 완료를 선언하지 않는다.

## 확인된 현재 흐름

`POST /api/v1/questions/chat`은 **인증된 요청만 허용한다.** `BenefitChatController`의 nullable principal 인자는 호출자를 익명으로 허용한다는 뜻이 아니다. `SecurityConfig`는 `/chat`을 public allowlist에 넣지 않고 `.anyRequest().authenticated()`로 닫는다. 서비스 직접 호출로 profile 없이 실행한 synthetic 사례는 익명 endpoint/API 인증 동작 검증이 아니다. 인증된 계정이라도 profile carrier/grade가 비어 있을 수 있으므로 이 상태를 분리해 다룬다. 서비스가 로그인 사용자 carrier/grade를 읽고 플래너가 요청·최대 12개 대화 메시지를 해석한다. AI 활성 시 planner LLM 호출을 하고, 대화 주제가 유효하면 embedding 생성 후 ES vector+lexical 검색, 실패/빈 결과면 DB lexical fallback을 시도한다. 후보를 정리한 다음 answerer LLM으로 이유와 candidate key를 고르고, 실패 시 결정론적 문장으로 fallback한다. 주변 요청은 답변 카드마다 별도 store enrichment가 수행된다. 참고: [SecurityConfig.java](../src/main/java/com/itplace/userapi/security/config/SecurityConfig.java#L122), [BenefitChatController.java](../src/main/java/com/itplace/userapi/ai/chat/BenefitChatController.java#L19), [BenefitChatService.java](../src/main/java/com/itplace/userapi/ai/chat/BenefitChatService.java#L44), [BenefitChatPlanner.java](../src/main/java/com/itplace/userapi/ai/chat/intent/BenefitChatPlanner.java#L52), [BenefitSearchServiceImpl.java](../src/main/java/com/itplace/userapi/ai/rag/service/BenefitSearchServiceImpl.java#L113), [BenefitChatAnswerer.java](../src/main/java/com/itplace/userapi/ai/chat/llm/BenefitChatAnswerer.java#L54).

이미 있는 보호 장치도 유지 대상이다. LLM 실패는 heuristic/결정론 답변으로 내려가고, 모델이 반환한 candidate key는 검색 후보 allowlist와 대조한다. grade가 지정되면 전 등급 또는 정확히 일치하는 등급만 허용한다. 현재 대화 history는 user role만 planner에 전달하고, answerer는 후속 질문일 때만 user 메시지를 받는다. 프롬프트에는 입력을 신뢰하지 말라는 지침이 있다. 참고: [BenefitChatPlanner.java](../src/main/java/com/itplace/userapi/ai/chat/intent/BenefitChatPlanner.java#L58), [BenefitChatAnswerer.java](../src/main/java/com/itplace/userapi/ai/chat/llm/BenefitChatAnswerer.java#L69), [BenefitSearchServiceImpl.java](../src/main/java/com/itplace/userapi/ai/rag/service/BenefitSearchServiceImpl.java#L212).

## 근거 기반 품질·지연 위험

1. **짧은 주제어는 한 개의 모델 해석에 품질이 크게 좌우된다.** 대표 fallback 분류는 편의점/영화/카페/키즈카페/스터디카페 등을 별도 정규화하지만, AI가 켜져 있으면 planner의 재해석 결과를 heuristic과 병합한다. 대화 주제 이력은 과거 사용자 문장에서 첫 topic을 얻고, follow-up 판정은 길이/키워드 규칙에 의존한다. 짧은 새 topic이나 혼합 topic은 `base`와 LLM plan의 병합 규칙에 따라 누락·오염될 수 있다. (`BenefitChatPlanner.java:78-121,124-183,193-226,354-370`)
2. **주제 분류는 RAG 색인기와 챗봇 필터가 따로 정의한다.** 색인 분류기는 partner/category/main category/benefit name/description/manual/tier context 전체에서 우선순위 키워드를 검색한다. 예컨대 `파고다어학원`은 partner name의 `학원`만으로 STUDY_SPACE에 분류된다. 교육기관의 장학금·수강 혜택이라면 actual benefit name/manual/context의 혜택 목적을 읽어야지 제휴처 이름이나 incidental 카페 단어만으로 주제 정답을 붙여서는 안 된다. 또 `스와로브스키` 이름만 보면 카페 주제가 아니지만 실제 `카페 스와로브스키` 혜택이 있으므로 partner명만 보고 배제해서도 안 된다. 분류 입력에 불필요한 manual keyword가 섞이면 업무 목적을 왜곡할 수 있다. (`BenefitRagMetadataClassifier.java:13-30,75-97`; 색인 입력/메타데이터 생성 `BenefitRagDocumentBuilder.java:67-85,144-179`)
3. **다중 주제와 넓은 검색의 강제 필터가 불완전하다.** 서비스는 `편의점`, `영화`, `카페/디저트`, `키즈카페`, `스터디카페`만 business type 필터로 바꾸고, `음료`, `외식`, `쇼핑`, 기타 카테고리는 이 필터에 연결하지 않는다. 혼합 topic은 생성된 businessTypes의 후보를 공유 검색 결과에서 다시 걸러내는 규칙도 통합 데이터 계약으로 분명하지 않다. 후보 분산은 검색 순서대로 partner 별로 round-robin하지만 relevance와 중복 혜택이 함께 남을 수 있다. (`BenefitChatService.java:154-181,184-198,231-249,265-283`)
4. **유사도 검색과 fallback의 비용 상한을 측정해야 한다.** queryChat은 요청당 ES vector 및 lexical 요청을 각각 실행한다. 임베딩이 없으면 의미 없는 일반어를 제거한 lexical 요청을 한 번 하고, 결과가 없으면 DB 후보를 최대 10,000개까지 불러와 Java에서 텍스트를 합치고 점수화한다. 이 경로는 품질 저하 상황에서 DB 부하가 커질 수 있다. `resolveChatCandidates`와 browse도 최대 10,000 후보를 다시 가져와 키/채널 필터링한다. 위치 요청은 최대 8개 응답 후보에 대해 매장 서비스 조회가 반복된다. 실제 지연은 분해 계측 없이는 단정할 수 없다. (`BenefitSearchServiceImpl.java:113-203,219-243,245-267`; `BenefitChatService.java:139-181,307-316`)
5. **답변 근거 크기와 답변 비용도 상한이 크다.** answerer 입력은 최대 후보 20개와 각 후보에 최대 manual 1,200자, context/description/조건을 담고 completion token 상한은 1,500이다. 검색 결과는 최대 40개이고 API 카드 최대 8개이므로, LLM 선택과 최종 카드 간에 출력이 더 짧더라도 후보 payload는 클 수 있다. 모델 호출은 planner+answerer 직렬이며 둘 다 설정 timeout 기본 8초를 사용한다. 이는 16초의 고정 지연을 뜻하지 않으며 실제 분포 계측이 필요하다. (`BenefitChatAnswerer.java:54-82,89-104,113-120,228-233`; `BenefitChatService.java:32-34,116`; `BenefitChatPlanner.java:41-49`)
6. **결정론 fallback도 근거 신뢰성을 보장하지 않으며 짧은 overview에 맞게 설계되지 않았다.** answerer는 최대 2개 후보의 description/context/manual/condition 일부를 모델 호출 없이 연결하고 제안 질문을 붙인다. 생성 모델 변동성은 줄지만, 원문 manual이 오래됐거나 틀렸거나 근거가 불명확하면 이를 그대로 답에 반영할 수 있다. 따라서 fallback은 `안전한 답변`으로 간주하지 말고, 동일한 검증된 근거·자격 규칙과 제한된 문구를 적용해야 한다. 임베딩 장애 시 검색은 lexical로 이어지고 retrieval 자체가 실패하면 UNAVAILABLE을 반환한다. “카페”처럼 한 단어 요청의 모델 비의존 overview도 아직 명세되어 있지 않다. (`BenefitChatAnswerer.java:107-139`; `BenefitChatService.java:63-88`)
7. **프로필·요청 등급의 의미와 노출을 엄격히 구분해야 한다.** endpoint가 인증을 요구하지만 가입/인증된 사용자 profile에 carrier나 grade 값이 없을 수 있다. 명시된 carrier/grade 및 대화 history가 해당 요청에서 profile보다 우선한다. 비교 요청은 명시적으로 “내 혜택”을 묻지 않는 한 grade를 비운다. 결과 카드에는 후보별 carrier/grade가 있지만 결과 문장에 적용 자격을 분명히 하는 별도 필드는 없다. 사용자에게 모르는 등급을 추정하지 말고, `프로필 기준`, `요청에서 지정`, `등급 미확인/전 등급`을 구분해 표현하는 기준이 필요하다. (`BenefitChatService.java:44-48`; `BenefitChatPlanner.java:85-98,145-163`; `BenefitChatAnswerer.java:129-136`; `BenefitChatResponse.java:12-16`; `SecurityConfig.java:122-132`)
8. **주변/지역은 현재 데이터 계약에 한계가 있다.** `lat/lng`는 좌표 쌍 유효성만 확인한다. 명시 지역 문자열은 별도 좌표로 변환하지 않고, 위치 카드 조회도 명시 지역이 비어 있고 좌표가 있을 때만 실행한다. 특정 지역의 실제 이용 가능 여부·영업 여부를 보장하지 않는다. 주변 검색 실패는 카드 없이 계속 진행한다. (`BenefitChatRequest.java:15-33`; `BenefitChatService.java:125-129,307-316`)

현재 결과 파일은 [서비스 baseline](evaluation/chat-service-baseline-2026-10-20.json)이다. 9개 synthetic 서비스 호출에서 `스터디카페` 검색이 파고다어학원을, `편의점 카페` 검색이 T 우주 신한카드와 스와로브스키를 반환했다. 파고다 결과는 partner name의 `학원`이 분류기의 `학원 → STUDY_SPACE` 규칙에 직접 걸리는 코드와 부합한다. 혼합 질의의 신한카드 원문에는 실제로 `T 우주패스 편의점&카페` 문구가 있어 제휴처명만으로 오답이라 부를 수 없다. 반면 다중 주제가 각각 충분히 다뤄졌는지, 카드 적립 혜택이 해당 이용 목적에 맞는지는 payload와 목적별 사람 판정으로 확인해야 한다. `카페 스와로브스키`도 실제 카페 혜택이므로 제휴처명만으로 걸러서는 안 된다. 현재 분류기는 manual을 포함한 전체 텍스트에서 `카페`를 `편의점`보다 우선 판정하므로 manual의 부수 키워드가 다른 후보를 포함시킬 가능성도 있으나, 개별 후보의 source evidence를 확인하기 전에 이를 해당 baseline의 단일 원인으로 확정하지 않는다. fallback 응답에는 반복되거나 잘린 듯한 rationale도 관찰되었다.

이 서비스 harness는 HTTP 상태, 인증 동작, end-to-end 지연이나 token usage를 측정하지 않았고, 9개가 전부 통과했다는 자료도 아니다. 동일 날짜의 [읽기 전용 로컬 snapshot](evaluation/local-readiness-snapshot-2026-10-20.json)은 production 검증이 아니다. 거기서는 PostgreSQL active policy 698건 모두 `usageType=BOTH`로 저장되어 있고, 구조화 conditions 0/698, `sourceCapturedAt` 0/698, `sourceUrl` 698/698이다. partner category는 443개 중 224개가 비어 있다. 즉 schema 필드나 `BOTH` 값의 존재만으로 online eligibility, 현재 유효성, 최신 사실을 입증하지 못한다. source URL이 있다는 것도 그 원문이 현재 검증됐다는 뜻이 아니다. ES `benefit` index 4,405건, `store` 0건이며 `questions`와 `question_embeddings` 모두 404였고, PostgreSQL에서 pgvector extension을 사용할 수 없었다. 따라서 store/question retrieval이나 pgvector 성능에 대한 주장은 할 수 없다.

## 목표 흐름 제안

1. **사용자 문장과 데이터 분류에 같은 canonical topic 체계 적용.** 공통 taxonomy에 topic ID, 동의어, 제외어/부정표현, 우선순위, 다중 주제 규칙을 둔다. source of truth는 가능하면 구조화된 제휴 분야·혜택 분야·혜택 유형이며, free text는 분류 보조 근거로 제한한다. 기존 `businessType`가 가진 명칭은 호환 매핑으로 유지한다. 제휴처 브랜드 자체는 보조 단서이지 정답 라벨이 아니며, 원문에서 업무 목적이 확인되지 않으면 `OTHER/미분류`로 보존하고 검색 가능한 텍스트에서 임의로 버리지 않는다.
2. **짧고 모호한 요청에 먼저 검증된 overview 반환.** “편의점”, “영화 할인”, “카페”는 통신사/등급을 받기 전에 물어보는 차단형 질문이 아니다. 기본은 확인된 대표 혜택 몇 개를 보여주고, 각 카드/문장에 적용 carrier와 등급 범위를 적는다. profile이 없거나 자격 정보가 없으면 “혜택 후보”로 표현하고, 사용 가능하다고 단정하지 않는다. 결과가 없거나 검색 불가할 때만 짧은 후속 질문/재시도를 제시한다.
3. **세션 상태보다 명시적인 현재 입력을 우선한다.** topic/carrier/grade/channel/location/exclusions를 별도 필드의 resolved plan으로 확정한다. 현재 질문이 topic을 바꾸면 이전 topic을 덮어쓰고, 명시적 제외와 여러 topic을 보존한다. 짧은 후속 표현은 직전 assistant 응답 카드의 candidate key와 현재 사용자 질문을 기준으로 연결한다. history는 제한된 문맥이며 지시를 실행하는 컨텍스트가 아니다. 애매한 “그거”에 여러 후보가 있으면 식별을 물어본다.
4. **검색 결과를 검증 가능한 랭킹/그룹으로 나눈다.** topic별 후보를 먼저 분류·필터하고 carrier 및 tier eligibility를 독립적으로 적용한다. 혼합 질문이면 topic 그룹을 별도로 확보해 일부 topic이 전부를 잠식하지 않게 한다. excluded partner는 후보 단계에서 제거한다. 정렬 점수/분류 근거는 내부 trace에 보관하고, 사용자에게는 검증되지 않은 인기도/위치/재고를 표시하지 않는다.
5. **고정된 요약은 결정론적으로, 언어 표현만 필요할 때 생성형으로.** 카드 선택과 자격/조건 수치는 코드에서 확정하고, LLM은 허용된 증거 기반의 간단한 요약/다음 질문만 만든다. 모델 장애·timeout·잘못된 JSON 시 동일한 compact overview를 반환한다. 검색 장애는 빈 결과로 위장하지 않고 기존 UNAVAILABLE 의미를 유지한다.
6. **PG/pgvector 전환은 검색 계약을 보존한다.** benefit/policy/tier 문서의 문서 키, active 상태, carrier·grade·all-grade, channel, topic metadata, 조건 필드와 `Candidate.candidateKey`를 독립 인덱스/DB 전환과 함께 검증한다. PostgreSQL 우선 통합 시 relational filter가 먼저 eligibility/topic을 적용하고, pgvector가 제한된 집합 안에서 순위를 내도록 후보 폭을 설계한다. hybrid lexical/vector 결합과 실패 fallback, 기존 ES 병행/되돌리기 방식은 migration 설계안에서 별도 확정해야 한다. ES와 DB의 중복 소스 쓰기 상태, 재색인/embedding 버전, 삭제·비활성 동기화의 소유권도 명시한다. 구체 pgvector 연산자/인덱스 선택과 비용은 데이터 크기·쿼리 계획·실측 전에는 고정하지 않는다.

## API/클라이언트 계약

현 endpoint와 envelope는 유지하는 것이 안전하다: `/api/v1/questions/chat`, `ApiResponse<BenefitChatResponse>`. 요청은 `question`, `messages`, `previousCandidateKeys`, `lat/lng`, 선택적 `carrier/grade`; 응답은 `reason`, `partners`, `status`, `suggestedQuestions`, `traceId`이다. 상태는 `ANSWER`, `CLARIFICATION`, `NO_RESULTS`, `UNAVAILABLE`, `OUT_OF_SCOPE`로 현재 웹 타입에 정의되어 있다. 파트너 카드의 식별 키는 benefit+policy+tier 조합의 `candidateKey`이며 follow-up에 다시 전달된다. 이 key semantics를 DB ID 변경과 분리하고, 데이터 migration 이후에도 현재 키를 resolve할 수 있어야 한다. ([BenefitChatRequest.java](../src/main/java/com/itplace/userapi/ai/chat/dto/BenefitChatRequest.java#L15), [BenefitChatResponse.java](../src/main/java/com/itplace/userapi/ai/chat/dto/BenefitChatResponse.java#L5), [questionRecommendation.ts](../../itplace-user-front/src/types/questionRecommendation.ts#L1), [QuestionRecommendationChatRoom.tsx](../../itplace-user-front/src/features/questionRecommendationChat/components/QuestionRecommendationChatRoom.tsx#L172))

웹 채팅 UI는 메시지 history와 직전 카드 key, 좌표, 재시도 상태를 전송한다. 앱은 현재 같은 `/chat`이 아니라 기존 `/api/v1/questions/recommend` GET을 호출한다. 그러므로 품질 개선 범위에 native chatbot UI/API 변경을 포함하는지 별도 범위 결정이 필요하다. 요청된 준비 단계에서는 앱 API를 변경하지 않는다. ([exploreApi.ts](../../itplace-user-app/src/features/explore/exploreApi.ts#L206))

## 비용·성능·품질 측정안

모델 가격이나 latency를 가정하지 않는다. 비용 확인 단계에서는 설정된 provider/model, planner/answerer 호출 여부, 입력·출력 token usage(제공되는 경우), timeout/fallback 비율을 환경별로 수집해 공급자 단가와 대조한다. 개인 질문·원문 조건을 로그에 복사하지 않고 trace ID와 길이/상태만 기록한다. 지연은 end-to-end와 planner, embedding, vector, lexical, DB fallback, answerer, store enrichment 단계별 p50/p95/p99 및 오류율을 나누고, warm/cold, AI on/off, ES 정상/실패, DB fallback에서 비교한다. 후보 개수와 request/evidence byte 크기도 함께 남긴다. 초기 제안 목표는 공통 readiness 기준과 일치시킨다: 동일 환경·고정 snapshot에서 동시 요청 10개, warm-up 후 검색 단계 p95 ≤ 300ms, 지도 keyword API p95 ≤ 500ms(AI 제외 여부 명시), 정상 AI 경로 HTTP p50 ≤ 4초·p95 ≤ 8초이며 planner/embedding/retrieval/answerer/store를 구간별로 분해한다. 전환 전 측정값이 없으므로 이는 달성값이 아니라 검증 목표다. OpenAI latency guide도 순차 모델 요청은 왕복 지연을 더하므로 요청 수를 줄이고, deterministic한 단계에서는 LLM을 기본값으로 두지 말라고 제안한다. 다만 우리 흐름에서 planner와 answerer를 합칠 수 있는지는 품질·근거 검증을 통과한 후 비교한다. ([Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization))

평가 corpus는 짧은 단일 topic(`편의점`, `영화 할인`, `카페`), 다중 topic(`편의점 카페`), 민감 혼동(`스터디카페` 대 일반 카페, 키즈카페, 이름은 카페지만 실제 목적이 다른 항목), 브랜드 명시, 여러 통신사 비교, 인증 계정의 profile carrier/grade 미기재, 후속 상세/ordinal/대안/주제 전환, partner/topic 제외, 온라인·오프라인, 지역+좌표/좌표 없음, 빈 결과, injection 문구, LLM·embedding·ES·DB·store 장애를 포함한다. endpoint 자체의 익명 접근 거부는 서비스 harness가 아니라 SecurityConfig/HTTP 통합 확인으로 별도 검증한다. 판정자는 query별 expected topic/carrier/grade/exclusions, precision@k/recall@k, topic coverage, partner duplication, 자격 정확성, 근거 문장 일치, unknown 의도 처리, status/fallback 계약을 확인한다. OpenAI 평가 지침에 따라 대표·경계·적대적 입력을 포함하고, 기계 검사 외에 사람의 relevance/evidence review와 명시적 pass/fail 기준을 둔다. ([Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices))

## 구현 작업으로 넘길 때의 분할·완료 조건

단계 의존성·파일 소유권 및 검색·API·성능 기준은 [통합 readiness 문서](search-chat-readiness.md)를 기준으로 한다. 아래 표는 챗봇 관점의 세부 수용 조건이다.

| 작업 | 소유 파일/영역 | 완료 조건 |
| --- | --- | --- |
| canonical topic/목적 taxonomy와 query resolution | API planner + RAG metadata classifier/document builder | 짧은·다중·제외·주제전환 corpus에서 주제 일치, 업무 목적 근거 없는 분류는 미분류 유지, 기존 `businessType`/문서 필드 호환 |
| overview·eligibility·follow-up 결과 정책 | API `BenefitChatService`, `BenefitChatAnswerer`, DTO는 필요 시 확장 | 프로필 기준/요청 기준/미확인/전 등급 표기를 구분, 임의 등급 추정 없음, 이전 candidate key 유효성·상세·ordinal·대안 회귀 없음 |
| PostgreSQL/pgvector와 hybrid search 전환 | 검색 service, entity/repository/index migration 모듈 (별도 migration 설계 확정 후) | active/삭제/정책/tier 조건 보존, top-k relevance 및 lexical fallback 측정, backfill·재시도·중복/rollback 운영 절차, 기존 API key resolve 유지 |
| 웹 계약 및 실제 소비 확인 | 웹 API type/채팅, 앱 recommendation 별도 판단 | 기존 envelope/status/key 처리 유지, retry·topic 전환·UNAVAILABLE 소비 유지, 범위에 넣는 경우 앱 호출 경로 별도 승인/설계 |
| 평가·관측 | API metrics/logging 및 corpus | 모델 호출·검색 단계 지표, 개인정보 비노출, 기준선 대비 품질/지연 비교, 오류별 fallback 확인 |

검증 게이트는 기존 분류기/문서 builder/search/chat 테스트, 평가 corpus와 추가 회귀 사례, API/auth 계약, 동일 snapshot의 검색 품질·latency 비교, 오류 fallback·복구·rollback을 포함한다. Hard safety/API assertions는 제외·carrier·grade 오답, 후보키 allowlist 위반, 확인되지 않은 online/현재 유효성 표현, 잘못된 status가 0건이어야 한다. relevance 숫자는 검토·버전 고정한 gold set과 coverage가 확인될 때만 비교하며, 미실행 케이스는 통과로 세지 않는다. 검색 품질·성능·데이터/동기화 수치는 [통합 readiness 문서](search-chat-readiness.md)의 제안 기준을 그대로 사용한다. PG/pgvector 전환의 데이터 계약과 단계별 제안은 [PostgreSQL 검색 전환 설계](postgres-search-transition.md)를 기준으로 검토한다. rollout과 웹/앱 포함 여부는 해당 단계에서 확정한다. 이 준비 단계에서는 Gradle 실행이나 유료 모델 호출을 하지 않았다.
